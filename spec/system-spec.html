CompoundEngine

A harness-agnostic state machine for Compounding Engineering: brainstorm → plan → work → codeReview → compound. One pure core, two ways to run it.

01Two drivers, one core

The state machine is the conductor, not a plugin. The same pure core (Phase · PhaseEvent · Transition) and the same compound binary power both an unattended Model A · headless orchestrator and an interactive Model B · harness plugin. Only the driver and the I/O seam differ.

02The state machine

A pure (State, Event) → State function. Bugs take the debug path, features take work; both converge on codeReview. Confidence-gated planning and bounded retries are encoded in the transitions — the model cannot skip a stage, and loops are provably finite.

stateDiagram-v2
  direction LR
  [*] --> brainstorm
  brainstorm --> plan: requirementsWritten
  brainstorm --> plan: routeToDebug (track=bug)
  plan --> plan: low confidence (deepen <= max)
  plan --> work: planWritten >= threshold (knowledge)
  plan --> debug: planWritten >= threshold (bug)
  plan --> failed: deepen exhausted
  work --> codeReview: codeWritten
  debug --> codeReview: codeWritten
  codeReview --> codeReview: verificationPassed (reviewers run)
  codeReview --> work: verificationFailed or reviewBlocked
  codeReview --> debug: bug-track loopback
  codeReview --> compound: reviewApproved
  codeReview --> failed: attempts exhausted
  compound --> [*]: compoundCaptured
  compoundRefresh --> [*]: refreshCompleted
  productPulse --> [*]: pulseWritten
Invariants the shape guarantees
  • Can't reach compound without passing Evidence + approved review.
  • deepen and verification retries are bounded → no infinite loops.
  • Illegal (phase, event) pairs are refused, recorded, never advanced.
Anchors & outer loop
  • strategy · ideate — re-runnable bookends feeding brainstorm.
  • productPulse — feeds the next cycle's brainstorm (the outer back-edge).
  • compoundRefresh — maintenance over docs/solutions.

03Model A — headless CI / unattended

compound run is the orchestrator loop. Phase = invocation boundary: one scoped claude -p / codex exec call per phase, the verification gate runs the tests itself, and the machine checkpoints after every transition (resumable after a crash).

sequenceDiagram
  autonumber
  participant O as Orchestrator (compound run)
  participant R as AgentRunner
  participant X as claude -p / codex exec
  participant G as VerificationGate
  participant K as KnowledgeStore
  participant S as Checkpoint
  loop until phase is terminal
    O->>R: run(WorkUnit for phase)
    R->>X: headless call (scoped --allowedTools / --sandbox)
    X-->>R: WorkResult
    R-->>O: StructuredResult
    O->>O: interpret() -> PhaseEvent
    opt phase == codeReview
      O->>G: verify (swift test / xcodebuild)
      G-->>O: Evidence or failure
    end
    O->>O: Transition.next()
    opt phase == compound
      O->>K: write SolutionDoc to docs/solutions
    end
    O->>S: checkpoint MachineState
  end

04Model B — harness plugin daily driver

A normal claude / codex session. Lifecycle hooks enforce the same invariants by shelling out to compound. SessionStart resumes state; PreToolUse is the firewall; Stop is the verification gate that refuses to end a turn on red tests.

sequenceDiagram
  autonumber
  actor Dev
  participant A as Agent (Claude Code / Codex)
  participant H as Lifecycle Hooks
  participant C as compound CLI
  participant S as .compound/state.json
  Dev->>A: open session
  A->>H: SessionStart
  H->>C: compound rehydrate
  C->>S: read MachineState
  C-->>H: additionalContext
  H-->>A: inject "phase=plan, read-only"
  Dev->>A: /ce-plan ...
  A->>H: PreToolUse (Edit)
  H->>C: compound policy --tool Edit
  C-->>H: exit 10 (deny + reason)
  H-->>A: permissionDecision: deny
  A->>H: Stop (turn end)
  H->>C: compound verify
  alt tests fail
    C-->>H: exit 1
    H-->>A: decision: block — keep going
  else tests pass
    C-->>H: exit 0 (+ Evidence)
    H->>C: compound advance --from-result
    C->>S: write next phase
    H-->>A: allow stop
  end
Because Codex reuses Claude Code's hook wire format, the same hook scripts drive both — see examples/shared/hooks/. Only the config files differ (.claude/settings.json vs ~/.codex/config.toml).

06Per-phase tool policy

The firewall compound policy enforces. Planning phases "plan, don't code": they may write their own docs/ and the engine's .compound/ control files, but not source. Only work/debug may mutate source or run shell; codeReview may verify but not edit. Meta-tools (Skill, AskUserQuestion, …) are never governed by the firewall.

07Persistence — the compounding substrate

Everything worth keeping is a repo-relative file. Capture (compound step) and retrieval (plan/debug search) are the two halves of the loop — capture without retrieval is inert.

repo/
├─ .compound/
│  ├─ state.json        # MachineState checkpoint (resumable)
│  ├─ result.json       # StructuredResult handed phase→machine
│  └─ audit.log         # append-only (phase,event,at) — compliance + evals
└─ docs/
   ├─ brainstorms/      # WHAT, not HOW
   ├─ plans/            # U-IDs, test scenarios, confidence
   ├─ solutions/        # <category>/*.md  — YAML frontmatter, two tracks
   │  ├─ ui-bugs/ · performance-issues/ · architecture-patterns/ ...
   └─ pulse-reports/    # outer feedback loop → next brainstorm

08Harness notes & the one real gap

Claude Code
  • ${CLAUDE_PROJECT_DIR} expands to repo root — paths just work.
  • PreToolUse covers every tool → complete in-session firewall.
  • Settings precedence: managed > local > project > user.
Codex CLI
  • Hooks engine is Claude-compatible, stable, default-on.
  • Use absolute hook paths (no ${CLAUDE_PROJECT_DIR}).
  • Use either [hooks] in config.toml or hooks.json, not both.
  • notify can't gate — fire-and-forget, one event.
The gap to design around. On Codex, PreToolUse fires for the shell tool but not yet for apply_patch (file edits) — openai/codex#16732. So the hook alone can't block edits during read-only phases. Mitigation, used in the example configs: enforce read-only phases at the sandbox level (sandbox_mode = "read-only", or per-phase codex exec --sandbox read-only) so writes are blocked by the OS regardless of tool coverage. The Stop verification gate and audit are unaffected.
